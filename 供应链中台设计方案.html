01

项目概述与设计原则

项目定位、核心目标、以及贯穿全部设计决策的基本原则。

背景

团队从事 B300 服务器及未来其他硬件板卡/整机的供应链上下游撮合业务。3-5 名成员分布在不同地区,需要共同维护一份数据库;任何账户的维护、更新都必须留有日志。

供应链分为三层:上游供货方(背后是海外链路方)、中间层(代开证/保函/居间等,1-2 层、国资居多)、下游客户(采购方)。

系统目标

  • 三层主体信息的分类化、结构化管理与定期维护;
  • 采购需求与供货信息的看板发布与全员可见;
  • 基于数据库的上游-下游自动匹配与衔接;
  • 订单全流程跟踪(货源 / 资金 / 到货 / 交付 / 违约);
  • 量化分析中台,呈现供应链变化与成交情况;
  • 全员操作全程留痕,可追溯、可审计。

设计原则

  • 云端轻量部署:单台腾讯云轻量服务器 + Docker 一键部署,7×24 后台运行,不用微服务、不用 K8s;
  • 数据归属清晰:每个用户独立维护自己的数据,共享需申请-审批,管理员全局可见;
  • 审计先行:一切修改写入审计日志(谁、何时、改了什么、改前/改后值),日志只增不改;
  • 产品线可扩展:型号作为独立维度,B300 是第一个产品线,新增板卡/整机型号无需改代码;
  • 并发兜底:共享数据共同维护场景下,用版本号乐观锁 + 编辑心跳 + 事务保护,杜绝互相覆盖;
  • UI 简洁高级:科技感、清爽、克制的色调,不因内部工具而马虎;
  • 拒绝过度设计:3-5 人规模,单体应用,能用简单方案解决就不上复杂组件。

用户体系 · 权限 · 数据共享 · 并发兜底

两级角色、数据归属清晰、共享有据、多人共改不丢数据。

3.1 角色与权限

角色数据可见范围操作权限
管理员全局:所有用户维护的全部数据(上游/中间层/下游/看板/订单)除普通用户全部功能外,还可:用户账号管理(创建/停用/重置密码)、查看全部共享关系与审计日志、协助修正他人数据(操作同样留痕)、仲裁共享冲突。
一般用户默认:仅自己创建维护的数据 + 全员公开的看板发布维护主体信息、发布看板、使用匹配、设置优先级、跟踪订单、申请/接受数据共享、查看自己数据的审计日志。
数据归属规则:每一条主体记录(供货方/客户/中间层/订单等)都带 owner(创建人) 字段,后端强制校验——权限校验在服务端执行,前端隐藏按钮只是体验优化,不是安全边界。

3.2 数据共享机制(申请-审批制)

图 3-1 数据归属与共享模型:默认隔离,共享经申请-审批生效,管理员天然全局可见

共享流程细节

  1. 发起申请:用户 A 在"共享管理"中选择目标用户 B,勾选共享范围(全部 / 上游 / 下游 / 中间层,可多选),提交;
  2. 通知与审批:B 收到站内通知(WebSocket 实时推送),批准或拒绝,可附理由;
  3. 生效:共享范围内,A、B 互相可见并共同维护;每条记录显示"最后维护人 + 维护时间";
  4. 解除:任一方发起解除,另一方确认后生效;解除后各自保留自己创建的数据,历史审计不删除;
  5. 留痕:申请、批准、拒绝、解除全部写入审计日志;管理员可见全部共享关系并可仲裁。

3.3 并发兜底机制(多人共改不丢数据)

图 3-2 并发兜底时序:版本号乐观锁保证"后保存的人不会覆盖先保存的人"
机制说明
版本号乐观锁每条主体记录带 version 字段;保存时按"读到的版本"校验,不一致则拒绝并弹出差异对比(哪些字段被谁修改),合并后重新保存。
编辑心跳进入编辑页即上报"编辑中";他人打开同一条记录时看到黄色提示"XXX 正在编辑,建议稍后再改";5 分钟无心跳自动释放,支持手动抢占(抢占留痕)。
事务保护所有写操作在数据库事务内;配额扣减、订单状态流转等关键操作加行级锁,杜绝超额分配。
冲突草稿版本冲突时,提交内容自动保存为"冲突草稿副本",可在草稿箱找回合并,数据零丢失。
全量审计每一次写操作(成功与失败)均记录:操作人、时间、IP、实体类型、实体 ID、改前值(JSON)、改后值(JSON)。

看板发布、自动匹配、优先级、分析中台、订单跟踪五大模块。

字段说明
发布类型采购需求 / 供货信息

5.2 自动匹配引擎(上游 ↔ 下游,不含中间层)

图 5-1 匹配引擎流程:硬过滤 → 软评分 → 归属裁剪,只匹配上游与下游,不涉及中间层;规则之上叠加 AI 语义层(见第 06 节)

5.3 优先级管理

  • 用户可对上游供货方、下游客户自行设置优先级(1-9 级或星标),仅对自己生效;
  • 未设置优先级时,默认按最近维护更新时间排序(越新越靠前);
  • 优先级在匹配评分中权重最高(30%),直接决定匹配结果排序;

三条铁律

  • 确定性优先:到期、逾期、金额核对等可用规则解决的问题不上 AI;AI 只做规则做不了的事——语义理解、判断与生成;

安全设计

虽然是内部小系统,数据是商业核心资产,安全不妥协。
层面措施
传输安全全站强制 HTTPS(WSS),Let's Encrypt 自动续期;HSTS 开启。
认证安全密码 bcrypt 加盐哈希;JWT 7 天有效期 + 刷新机制;连续 5 次登录失败锁定账号 30 分钟并记录日志;管理员可强制下线某账号。
数据隔离后端强制校验数据归属:所有查询/写入按 owner 与共享关系过滤,前端隐藏不构成安全边界;API 层统一鉴权中间件。
注入与攻击SQL 全参数化(ORM);XSS 输出转义;CSRF 防护;接口限流。
附件安全上传白名单(类型/大小);存储于非公开目录,经鉴权接口下载,下载留痕。
备份容灾每日全量备份(本地 30 天 + COS 冷备);备份失败告警;提供一键恢复脚本与季度恢复演练。
审计不可抵赖审计日志只增不改,管理员亦不可删除;提供按人/实体/时间的检索与导出。

风险与应对

风险应对
多人共改同一数据导致覆盖版本号乐观锁 + 编辑心跳 + 冲突草稿副本 + 全量审计(见 3.3),已从机制上杜绝。
数据敏感(价格/配额/客户账户)归属隔离 + 共享审批 + 字段级可见控制 + HTTPS + 审计不可删。
单台服务器故障轻量服务器故障率低;每日备份 + COS 冷备,可在 1 小时内换机恢复;对 3-5 人内部系统,风险可接受。
业务演进(新交易模式/新字段)产品线独立维度;主体字段分组化设计,新增字段仅加列;中间层"目的"为多选字典,可扩展。
用户操作习惯(不习惯填结构化字段)提供 Excel 批量导入模板;必填项最小化;历史数据一次性导入;上线前培训 1 小时。
服务器运维能力不足Docker 一键部署/升级/备份脚本;本方案附运维手册;必要时由我远程协助。
